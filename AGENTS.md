# Project Runtime Console

This repository is intentionally small and reuse-first.

## Startup

1. Read `README.md`, `docs/NORTH_STAR.md`, and `docs/current-state.md`.
2. Run `git status --short --branch`.
3. Inspect the retained runtime substrate and current V1 evidence before editing.
4. Keep production runtime facts, native lineage, and shadow-only judgment semantics separate.

## Boundaries

- Preserve read-only Codex runtime observation and native identity.
- Shadow judgments never block, mutate, stop, or trigger Codex execution.
- Never invent agent lineage, outcomes, task boundaries, or provider results.
- Keep raw private transcripts, credentials, hidden reasoning, and secrets out of Git.
- Do not add a new graph/layout system, orchestration layer, task board, control plane, or active-intervention UI.
- Retain only evidence and code that serve the current reuse-first V1 question.

## Evidence

Claims about compatibility or progress require a real artifact or interaction result. Distinguish `CONFIRMED`, `UNAVAILABLE`, `INCONCLUSIVE`, and `UNKNOWN`. A passing test proves implementation behavior only; it does not prove that an upstream capability is suitable for PRC.

Human-facing summaries must be understandable Chinese; original evidence retains its language. Cleanup is not acceptance of a new UI.

## PRC execution and review

- Claude Code is the sole product writer for this project; do not automatically delegate implementation to Codex. Independent reviewers are read-only.
- Work explains work-content evolution; Agents explains execution structure and process; Trace explains concrete execution; the sidebar answers task, change, and actual result. Identity/role fields and raw logs do not replace these outcomes.
- B2/C are approved experience foundations. Define the exact layer updated by Langfuse/ThoughtDAG references before implementing; do not freeze conflicting standards.
- Before new implementation, prepare a bounded proposal and independent global review. First give the reviewer user-approved outcomes, reference identities and known failure examples, without the author's solution narrative. Then disclose the proposal separately. Review must consider whole-path value, fidelity, regressions and evidence, not just compliance with the author's spec.
- Automatic commits are conditional on the user's activation and demonstrated acceptable earlier rounds plus independent review. Explicit authorization for a cleanup commit/push is not authorization to merge, force-push or publish private evidence.
- Issues are the shared planning index. Keep local transcript-derived notes out of public Issues and commits. A decision Issue is not an implementation authorization.
